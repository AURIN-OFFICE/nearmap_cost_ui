# Cost Estimation — Validation Report

Generated by `python -m api_cost_estimation.validation.generate_report`. §1–§4 are **offline**, derived from the cached `data/credit_plans/*.json` (a `preview=true` snapshot from the ../nearmap repo, May 2026). §5 records a **live** `preview=true` run (also **$0**). No credits are charged anywhere.

## TL;DR — why `by_api_return` is the figure to trust

`by_api_return` is **the number Nearmap actually bills** (preview cost == real cost, validated as T1 in ../nearmap). `by_area` is a surprisingly good local model — it even reproduces Nearmap's two sublinear **bundles** (the >7-pack cap and the 1.5× multi-survey price; see §3–§4). Its blind spots are about *reality*, not *pricing math*:

- **Coverage (the blind spot this offline data exposes) → `by_area` OVER-charges coastal / partial-coverage AOIs by ~25–33%** (the Perth rows below). It bills the whole drawn polygon; Nearmap bills **0** for ocean / uncovered / out-of-date-window tiles, which `by_area` can't see.

- **Entitlements** — `by_area` also prices packs your account can't access; the live API rejects them (`403` / `UNKNOWN_PACK`). (Confirmed live — see §5.)

- **Everything else agrees:** over fully-covered land with packs you own, the two match to ~0.1% — including both bundle cases below. So `by_area` is a fine sanity check; trust `by_api_return` as the figure, chiefly because of coverage + entitlements.

## 2. No-coverage vs errored tiles (caveat A)

Not every skipped tile means the same thing. `adelaide_sample_pavement_condition` requested an invalid resource, so all 42 tiles **errored** → the total reads **0**, a silently-low number. The code therefore splits skipped tiles by reason:

- **`tiles_no_coverage`** — HTTP 404 (ocean / outside the date window). Nearmap charges nothing, so 0 is the **correct** price and the figure stays exact.
- **`tiles_errored`** — timeout / 5xx / 429 / 400. These *could* hide real cost, so the UI shows `≥ X` (or `API error` if nothing was priced).

That's why an all-ocean AOI shows an exact total, while a flaky run shows `≥`.

## 3. AI-pack bundle — >7 packs cap at the all-packs price

`cost_table.json` lists **AI (all packs) = 35 = 7 × AI (1 pack) (5)** (and 52.5 = 7 × 7.5 for all-survey). So AI-pack cost is `min(N, 7) × 5` per 1000 sqm — buying 8+ packs costs the same as 7. `by_area`'s cap-at-7 encodes exactly this, and the live API applies it too (empirically: selecting 10+ packs returned ≈ the 7-pack cost). So this is a **bundle both methods model the same way — not a divergence.**

## 4. Multi-survey bundle — `dates=all` ≈ 1.5× single

Every row in `cost_table.json` (and the rate table `by_area` uses) prices **all-survey data at exactly 1.5× the single-survey price** — e.g. AI pack 5 → 7.5, Vertical 10 → 15. `../nearmap`'s T7 confirmed this live: `dates=all` returned ~20 surveys for ~1.5× the cost of one (sublinear, ~0.75 cr/survey). `by_area` applies that 1.5× column when `dates=all`, so — like the AI-pack bundle — **both methods agree.** (Cached plans are all `dates=single`, so this is verified from the rate table + T7, not the §1 rows.)

## Key takeaways

1. **Trust `by_api_return`** — it is the billed number; `by_area` is a sanity check.
2. **Coverage is `by_area`'s main blind spot:** it over-estimates coastal / edge AOIs (bills free ocean tiles).
3. **Entitlements:** `by_area` prices packs you can't access; the live API rejects them.
4. **Both pricing bundles are modeled correctly by both methods** — >7 AI packs cap at the all-packs price (§3), and `dates=all` ≈ 1.5× single (§4). Pack/survey count is *not* where `by_area` goes wrong.
5. **A 404 is a real $0, not an error** — only genuine errors turn the figure into a `≥` lower bound.
6. The GDAL-free tiler reproduces the original tiling exactly (`repro_ok` column).
